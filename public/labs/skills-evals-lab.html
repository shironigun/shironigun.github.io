LLMs from zero: what you are actually testing

Before you can test a skill, you need a working picture of the thing that runs it. You do not need the maths of how models are trained. You need ten ideas, and each one changes how you write a test.

Tap any dotted-underlined term, on any page, to see what it means. Notation that is not a plain word, such as pass@k or τ-bench, also shows how to say it aloud. Every term is listed in the glossary.

Large language model (LLM)say “el-el-em”

Software trained on huge amounts of text to predict what text should come next. Given everything in front of it, it writes its answer one small piece at a time, each piece chosen based on all the text so far. It does not look anything up unless it is given a tool to do so. Claude is an LLM.

Why it matters for testing: Being fluent and wrong at the same time is normal for an LLM. A confident, well-written answer is not evidence that it is correct, so every test needs a grader that checks content, not tone.

Token

The small chunk of text a model reads and writes: often a whole short word, sometimes part of a long word or a punctuation mark. Limits, speed and cost are all counted in tokens rather than words or characters.

Why it matters for testing: A skill’s name and description cost about 100 tokens, and its body should stay under 5,000. Tokens per successful task is a real metric: a skill that doubles quality but triples tokens may not be worth it. Documented

Context window

The total text the model can see in a single request: instructions, the conversation so far, files it has opened, and tool results. Inside the window it can use everything. Outside it, nothing exists for the model.

Why it matters for testing: When a skill “ignores” a rule, check the transcript first. If the reference file holding that rule was never opened, the model never saw it. That is a loading problem, not a reasoning problem.

System prompt and user message

The system prompt is instructions set by the application, placed before the conversation. User messages are whatever the person types or pastes. On Claude, every installed skill’s name and description sits in the system prompt.

Why it matters for testing: Text a user pastes, such as an acceptance criterion, is data. Prompt-injection tests check that instructions hidden inside that data are not obeyed. Documented

Sampling and temperature

At every step the model has many possible next tokens, each with a probability. Sampling means picking one with some randomness. Temperature is a setting that controls how much randomness: higher gives more varied output, lower gives more repeatable output.

Why it matters for testing: This is why the same input can pass on one run and fail on the next. Report rates over several trials, never a single run, and do not assume identical outputs even at a low temperature. Pattern

Deterministic and stochastic

Deterministic means the same input always gives the same output, like an ordinary function or a code check. Stochastic means chance is involved, so the same input can give different outputs, like an LLM.

Why it matters for testing: The system you test is stochastic, but your graders should be deterministic wherever possible. Then a change in score means the system changed, not the grader.

Hallucination

Output that sounds right but is not supported by the input or by fact. When an LLM writes test cases, the most common form is an invented requirement.

Why it matters for testing: In the CSV-import example, a skill that states “files over 10 MB are rejected” when the story never mentions size has hallucinated a rule. Write assertions that catch invented facts, not only missing ones.

Tools and tool calls

A tool is an action the application offers the model, such as “run a bash command” or “search tickets”. The model cannot run anything itself. It writes a request, called a tool call; your application or Anthropic’s servers execute it; and the result goes back into the context.

Why it matters for testing: A tool call in a transcript is only a request. Check the tool result to see what actually happened, and test what the model does when a tool fails or times out. Documented

Agent and the agent loop

An agent is a model running in a loop: decide a step, call a tool, read the result, decide the next step, until it judges the task done. The software that runs this loop, records it and applies graders is called the harness.

Why it matters for testing: A correct final answer can hide a wrong or unsafe path, such as a write action that should never have happened. Read transcripts, and put assertions on tool calls as well as on the final text.

Model tiers: Haiku, Sonnet, Opus

Anthropic’s model families, from fastest and cheapest to most capable. The same skill can behave differently on each.

Why it matters for testing: Anthropic asks for skills to be tested on Haiku, Sonnet and Opus. Fix and record the exact model version in every eval run, otherwise you cannot tell a skill change from a model change. Documented

What a skill actually is

A skill is a folder. Its SKILL.md file has a short name and description, followed by instructions. Optional scripts, reference files and templates sit beside it. Claude loads it only when the task in front of it matches the description.

Anthropic’s definition: skills are modular capabilities that package instructions, metadata and optional resources, which Claude uses automatically when relevant. Documented Agent Skills overview

It loads in three levels

This is called progressive disclosure. It matters for testing because each level is a separate thing that can fail.

Level 1Always loaded
Name and description, placed in the system prompt at startup. About 100 tokens per skill. This is the only thing Claude sees when deciding whether to use the skill.
Level 2When triggered
The SKILL.md body, under 5,000 tokens. Claude reads the file once it decides the skill applies.
Level 3As needed
Reference files are read only if the instructions call for them. Scripts are executed, and only their output enters the context.

Token figures and loading behaviour: Documented Agent Skills overview

You can see it happen in the trace

On the Claude API, Claude opens a skill by running a bash command such as cat pdf-processing/SKILL.md inside the code execution container. That means “was the skill used?” is not a guess. It is a tool call you can find in the transcript. Claude Code exposes a dedicated Skill tool call that serves the same purpose. Documented

The one thing to remember: the description is the routing contract. If it is vague, the best instructions in the world never get read. Write it to say both what the skill does and when to use it.

One trap: Claude only consults skills for work it cannot easily handle on its own. A trivial prompt such as “read this PDF” may not trigger a skill even when the description matches perfectly. Trigger tests must use realistic, detailed requests. Documented skill-creator

When a skill should and should not fire

A skill meets very different situations: requests it was built for, requests that only look similar, inputs that are incomplete or hostile, and environments that differ. Each one is a condition you will test.

1. Will it fire? Six kinds of request

Sort each request for ui-test-case-writer, using only its description. Then read why.

The rules behind the sorting

  • A clear match should fire. A realistic request that matches the description.
  • A near-miss should stay quiet. It shares words with the skill but is another skill’s job, or no skill’s.
  • Ambiguous requests need a decision. Agree with your team what should happen, then test for that. Never leave them out of the test set.
  • Trivial requests may not fire even when they match. Claude does not reach for a skill on simple one-step tasks. Documented
  • Explicit invocation skips the decision. In Claude Code, typing /skill-name loads a skill directly, and disable-model-invocation: true makes a skill load only that way. Documented
  • Other skills compete. When several skills are installed, overlapping descriptions take each other’s requests. Test with every production skill installed. Documented

The only two genuinely new ideas

1. Results are rates, not single verdicts

A test that passes once can fail on the next run with identical input. So you run each task several times and report a rate. Two numbers dominate agent evaluation, and you will say them out loud in reviews, so learn the names as well as the maths.

pass@ksay “pass at k”

The question it answers: if the skill gets k attempts at a task, what is the chance that at least one attempt succeeds?

Plain example: a skill works 3 times out of 4. Give it 3 tries at the same task, and at least one will work about 98 times in 100.

Use it when a person or a later check picks the best of several attempts, so one success is enough. For example, you generate three drafts of a test suite and a QA analyst keeps the best one.

Show the maths

With a per-trial success rate p: pass@k = 1 − (1 − p)^k, which is one minus the chance that every attempt fails. For p = 0.75 and k = 3, all three fail with probability 0.25 × 0.25 × 0.25 ≈ 0.016, so pass@3 ≈ 98.4%.

Origin: code-generation benchmarks, where a problem counts as solved if any of k generated programs passes its unit tests. Pattern

pass^ksay “pass hat k” or “pass to the k”

The question it answers: if the skill runs k times, what is the chance that every run succeeds?

Plain example: the same skill, working 3 times out of 4, run 3 times: all three runs work only about 42 times in 100. A skill that looks “75% good” gives three users in a row a correct result less than half the time.

Use it when no person checks each run: a skill used many times a day by many people, or an automated step in a pipeline. This is the right number for most production skills.

Show the maths

With a per-trial success rate p: pass^k = p^k, which is p multiplied by itself k times. For p = 0.75 and k = 3: 0.75 × 0.75 × 0.75 ≈ 0.42.

Introduced by τ-bench (say “tau bench”; tau rhymes with “cow”). Its authors found that even gpt-4o, a strong tool-using agent at the time, succeeded on fewer than half the tasks, and below 25% at pass^8 in the retail domain. Documented arXiv 2406.12045

The short version: pass@k asks “did it work at least once?”, and pass^k asks “did it work every time?”. For a skill that people rely on without checking each result, pass^k is the number that matters. The formulas for measured data are in the eval lead track.

Definitions and the 0.75 worked example: Documented Anthropic, Demystifying evals for AI agents.

2. Some expected results are a rubric, not an exact value

“The test cases cover every acceptance criterion” cannot be checked with an equality assertion. You write a rubric, and a grader (a person or an LLM judge) scores against it. That grader then needs testing itself; the eval lead track covers how.

Three kinds of grader, in order of preference

Code

Regex, JSON schema, “file exists”, “database row matches”. Fast, cheap, never drifts. Use it wherever you can.

LLM judge

A model scores output against a written rubric. Use it only for what code cannot check, and only after calibrating it against human labels.

Human

The ground truth. Too slow to run on everything, so use it to label a sample and calibrate the judge.

Grader guidance Documented (Anthropic): grade what the agent produced, not the path it took; give each LLM judge one rubric dimension; let judges answer “Unknown”; read transcripts before trusting any score.

Capability evals and regression evals

A capability eval asks “what can it do?” and should start with a low pass rate, otherwise it has no room to show progress. A regression eval asks “did we break anything?” and should sit near 100%. The same tasks often move from the first kind to the second once the skill handles them. Documented

Every skill needs four separate tests

Each one catches a different failure, and passing one tells you nothing about the others. A skill with perfect output that never triggers is worth zero. The next lesson turns these into a checklist you use on every skill.

  1. Spec check: is the package valid?Static checks on SKILL.md: name format, description length, a “when to use” clause, body size. Cheap and deterministic. Run it on every commit. Lab: check a SKILL.md.
  2. Trigger test: does it fire at the right time?Queries labelled “should fire” and “should not fire”, including near-misses that share keywords with the skill. Each request runs several times, and passes only if the skill fires every time it should and stays quiet every time it should not. Repeat with your other skills loaded, because overlapping descriptions steal each other’s traffic. Lab: does it fire?.
  3. Uplift test: is it actually better than nothing?Run the same tasks with and without the skill (or against the previous version), with the same model and the same graders. The skill’s value is the difference. If the difference is zero, delete the skill. Lab: better than nothing?.
  4. Reliability test: does it work every time?Repeat the runs and count the tasks that worked every time, which eval leads report as pass^k. Customer-facing CRM workflows need consistency, not one lucky run. Lab: better than nothing?.

Cross-cutting rule: the author of a skill must not be its grader. Anthropic’s enterprise guidance says skill authors should not be their own reviewers. A separate agent, or a person, does the grading. Documented

Why some requests are set aside

You will rewrite the description to fix failures. If you then score it on the same requests you fixed it against, the score looks better than it really is. So mark a few requests as final check, do not use them while fixing, and score them once at the end. Anthropic’s skill-creator works the same way: it tunes the description on part of its queries and judges the result on the rest. Documented

What makes a good request

  • Realistic and detailed. Claude does not reach for a skill on trivial one-line tasks, so “write tests” is not a fair trigger test. Documented
  • Near-misses on the “No” side. Requests that share words with the skill, such as “test” and “story”, but need something else.
  • Balanced. Roughly as many “No” requests as “Yes” requests.

Why “worked every time” matters

A task that passed 2 of 3 times with the skill is not a reliable success. If dozens of people use the skill every day, “two times out of three” means it fails someone every day. The “worked every time” count is the plain-language version of pass^k with k = 3. Documented

2. Read the transcript

Check the output format: JSON, schema and rules

Many skills return JSON that another program reads directly. If the JSON is malformed, wrapped in extra text or has one field wrong, that program breaks, however good the content is. So every run’s output gets a format test before anything else.

The skill here is sms-owed-items-review, which reads one dealership SMS conversation and returns what the dealership still owes the customer, as JSON. Its output contract is written as a JSON schema: a machine-readable description of which fields must exist, their types, which values are allowed, and their limits. If you have written a zod contract test for an API, this is the same idea applied to a model’s output. Illustrative

  1. Load “Code fence”. The JSON inside is perfect, but the format check fails: the program reading it expects JSON and nothing else.
  2. Load “Fulfilled item still has urgency”. The schema passes, but a rule fails. A schema cannot express how fields depend on each other.
  3. Load “Reply too long”, then delete "maxLength": 320, from the schema. The problem disappears: a schema is only as strict as you write it.

How to use this in a real eval

  • Run it on every trial, first. It is a deterministic code check, the cheapest and most reliable kind of grader. There is no point judging the content of output that will not parse. Documented (Anthropic: deterministic graders wherever possible)
  • Mark format and schema failures critical. For a skill whose output feeds the CRM, invalid JSON is an outage, not a style issue.
  • Keep the schema in version control next to the skill, and test the schema itself: load deliberately broken outputs, like the presets above, and confirm each one fails. A schema that passes everything protects nothing.
  • Count format failures across runs. One malformed output in 20 runs is a 5% failure rate on every customer conversation.

Build your test set

The eval tool is the easy part. The test cases are the real work, and nobody publishes them for your CRM. You write them from your own stories, tickets and past bugs.

Four rules

  • Start from real failures, not imagined ones. Twenty to fifty cases is a real start. Documented
  • Write expected behaviour you can see in the output. “Lists duplicate handling as an open question” is checkable; “writes good tests” is not. Two people should reach the same verdict on every case. Documented
  • Never invent business rules. If the story is silent about duplicates, the right behaviour is to flag the gap, not to guess a rule.
  • Set some aside, and mark the dangerous ones. Final-check cases are scored once at the end. Critical cases fail the skill on their own.

The sample uses the story “As a CRM administrator, I want to import customers from a CSV file so that I can add multiple customers efficiently.” It leaves out required columns, duplicate handling, invalid rows, file size, encoding, partial imports, error reporting and permissions, so a good skill should flag those gaps. Your first real eval, in two weeks

Reading more will not make you good at this. Running one small eval from start to finish will. Pick one production skill and follow these steps.

  1. Pick one skill and write down its job (day 1)What it does, when it should fire, and what a good output looks like. If that takes more than five lines, the skill is doing too much.
  2. Check its SKILL.md (day 1)Run it through the SKILL.md check and fix every failure.
  3. Write 10 “does it fire?” requests (day 2)Five that should fire and five near-misses that should not. Use real portal requests where you can. Mark 3 of them as final check.
  4. Write 5 to 10 tasks (days 3 and 4)Real stories or tickets, each with an expected behaviour you can see in the output. Include at least one hidden-instruction case and mark it critical.
  5. Run each task 3 times without the skill and 3 times with it (day 5)Same model every time, starting fresh each run. Save the transcripts, not just the results.
  6. Read every transcript (week 2)Did the skill load? Did it open the files it needed? Did it try anything it should not?
  7. Grade each output with the rubricAny critical failure fails the output, whatever the total.
  8. Hand your sheet to the eval leadPer-request results, wins, ties and losses per task, and every critical failure by case ID. The eval lead decides whether the evidence is strong enough to release.

Done means

  • Every item on the mandatory checklist ticked
  • For a skill that returns JSON: every run’s output checked for format, schema and rules
  • The SKILL.md check shows no failures
  • 10 requests scored, with the 3 final-check ones reported separately
  • 5 to 10 tasks run 3 times each way
  • Every transcript read, and every critical failure listed by case ID
  • The test cases saved next to the skill in version control

Measure it properly

The associate labs describe results in plain words. This lesson gives you the formulas behind them, so you can report each number with its denominator and know how far to trust it.

What each number means

Every individual run counts as one observation. TP means it fired and should have. FN means it should have fired and did not. FP means it fired and should not have. TN means it stayed quiet correctly.

MetricFormulaPlain question
PrecisionTP / (TP + FP)When it fired, how often was that right?
RecallTP / (TP + FN)When it should have fired, how often did it?
False-positive rateFP / (FP + TN)When it should have stayed quiet, how often did it fire anyway?
F12PR / (P + R)One number balancing precision and recall

Why there is a train and test split

You will rewrite the description to fix failures. If you tune it against every query and then report the score on those same queries, the score is inflated, because you have fitted the description to the test. Anthropic’s skill-creator uses about 20 queries (8 to 10 of each kind), runs each 3 times, tunes on 60%, and selects the best description by its score on the held-out 40%. Documented skill-creator

Honest limits: 10 queries times 3 runs is enough to catch a badly broken description, not to tell 80% from 85%. Treat small differences as noise.

pass@k and pass^k from measured data

Three facts that trip people up. At k = 1 both numbers equal p, so pass@1 is simply the pass rate. As k grows, pass@k climbs toward 100% while pass^k falls toward zero, so the gap between them shows how inconsistent a skill is. And when you have measured data instead of a known p (n trials of which c passed), you use counting formulas instead: pass@k = 1 − C(n−c, k) / C(n, k) and pass^k = C(c, k) / C(n, k). For n = 3, c = 2 and k = 2, that gives pass@2 = 100% and pass^2 = 33%. Is the uplift real? calculates both for you. Pattern

Reliability calculator

pass@k = 1 − (1 − p)^k. pass^k = p^k. At p = 0.75 and k = 3, pass^k is about 42%, the worked example in Anthropic’s eval guide. Documented

How much a small sample can tell you

The standard error of a pass rate measured on n tasks is about √(p × (1 − p) / n). For 20 tasks at a 50% pass rate that is about 0.11, so a 95% interval runs roughly 22 points either side of the result. A small eval can catch a broken skill. It cannot tell 80% from 85%. Documented Formula from Miller, Adding Error Bars to Evals; the 20-task figure is a worked example.

How the verdict is calculated

For each task, take the with-skill pass rate minus the baseline pass rate. Average those differences across tasks. The standard error is the standard deviation of the differences divided by the square root of the number of tasks. The 95% interval uses a t critical value because task counts are small. If the whole interval sits above zero, the uplift is supported. If the interval includes zero, the change may be noise.

Paired, per-question differences and clustering trials by task follow Miller, Adding Error Bars to Evals. Documented arXiv 2411.00640. The per-task pass@k and pass^k estimators below use the combinatorial form C(c,k)/C(n,k) Pattern.

What research says about judges

Strong LLM judges reached over 80% agreement with human preferences, about the same rate at which humans agree with each other. The same study found position bias, verbosity bias and self-enhancement bias. Documented Zheng et al., arXiv 2306.05685

Shankar and colleagues found “criteria drift”: people often only discover the right grading criteria after reading real outputs. Expect to rewrite your rubric after the first round of transcripts, and recalibrate the judge each time you do. Documented Who Validates the Validators?, arXiv 2404.12272

Cohen’s kappa corrects raw agreement for the agreement you would get by chance. Bands such as “0.8 and above is strong” are common rules of thumb, not a standard. Pattern

Release gate

Before you sign off a skill, require all of these.

  • A lint report with zero failures
  • Trigger precision, recall and false-positive rate on the held-out split
  • Uplift with a 95% interval that excludes zero, or an honest “not shown”
  • pass^3 for each critical task
  • Zero critical failures, listed by case id
  • The dataset committed to version control next to the skill
